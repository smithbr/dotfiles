# scripts/bootstrap/

OS bootstrap that runs before anything is linked (`macos/setup.sh`, `linux/setup.sh`; both take `-n` to report what they would install), `linux/harden.sh` and its check `linux/harden-test.sh`, which `install.sh` offers before anything else on an unhardened server, and the setup scripts `install.sh` applies at the end: the optional installs every persona gets, on by default (`linux/docker.sh`, `linux/tailscale.sh`, `macos/holeberry.sh`, and `claude-code.sh`, shared by both OSes; each carries a `# detect: COMMAND` line, which is what makes it one, and the command-line tools detect with `tool_installed` from `scripts/common.sh` so a tool that came through Homebrew or natively is not installed again), and the roles' scripts ([`roles/`](../../roles/README.md): `linux/pihole.sh`). A new setup script is a file here named after its install or role, safe to run again, that skips what is already installed. The installation rules in the [root `AGENTS.md`](../../AGENTS.md) apply here first of all: no reliance on the current PATH, closed stdin never hangs or opts in, and every run is safe to repeat. Which manager installs a package, including system daemons that come through a vendor script here, is in [`homebrew/README.md`](../../homebrew/README.md).

## Linux

- `linux/setup.sh` installs `apt-packages.txt`.
- `linux/pihole.sh` sets up Pi-hole v6 with Unbound as its upstream, the way the [Pi-hole guide](https://docs.pi-hole.net/guides/dns/unbound/) describes and `ph-test` checks. Unbound comes from apt with the guide's `/etc/unbound/unbound.conf.d/pi-hole.conf` (loopback only on `127.0.0.1#5335`, DNSSEC validation, `harden-*`, `hide-*`, the private ranges kept out of answers), Debian's `unbound-resolvconf` hook is disabled (it would make Unbound the box's own resolver with the DHCP servers as forwarders), `net.core.rmem_max` is raised in `/etc/sysctl.d/99-unbound.conf` for `so-rcvbuf`, and `unbound-checkconf` must pass before Unbound is enabled and, when anything changed, restarted; a `dig` against the new socket confirms it answers. Pi-hole then comes from its official installer, unattended: the installer only skips its dialogs when `/etc/pihole/pihole.toml` exists, so a minimal one is written first with the upstreams from `PIHOLE_UPSTREAMS` (default `127.0.0.1#5335`) and `dnssec = false` (Unbound validates), and FTL fills in the rest. An installed Pi-hole is left to `pihole -up`, but every run brings its upstreams and DNSSEC setting back in line through `pihole-FTL --config`. The seeded install sets no web password; `sudo pihole setpassword` is the next step. It needs root and re-runs itself through sudo. `PIHOLE_ROOT` prefixes every system path, so the tests run it against a scratch tree with the commands mocked.
- `linux/harden.sh` locks down a Debian/Ubuntu server or VPS. It is never run unasked: on a server already in use (the Pi-hole) it would close every port but the tailnet's and allow only one SSH user, so `install.sh` only offers it, first, before anything is installed, on a Linux `server` or `vps` that `harden-test.sh --brief` finds unhardened (`--harden` and `--no-harden` answer without a terminal; closed stdin skips it; `HARDEN_ARGS` adds its options). Run from the repo as the admin user, it re-runs itself through sudo for that user. Run as root on a box that has no admin user yet, it creates one; it needs nothing else from the repo, so it can be piped over SSH: `ssh root@HOST 'bash -s -- --user NAME --allow 80 --allow 443' < scripts/bootstrap/linux/harden.sh` (`--cloudflare` opens the `--allow` ports only to Cloudflare's ranges, `--keep-public-ssh` keeps SSH open to the internet with rate limiting, `-n` is a dry run, and `TS_AUTHKEY` joins the tailnet without a login URL). It upgrades packages, creates the admin user with passwordless sudo and the keys you logged in with (root's, or `SUDO_USER`'s), installs and connects Tailscale, writes `/etc/ssh/sshd_config.d/00-harden.conf` (keys only, no root login, only that user; checked with `sshd -t` and put back if it fails), sets ufw to deny all inbound except `tailscale0`, Tailscale's UDP port, and the `--allow` ports, and turns on unattended upgrades. It stops before changing anything when there is no key to give the user, leaves public SSH open until Tailscale is connected, and without a terminal (an unattended install) does not wait for a Tailscale login. Running it again only changes what differs. Docker-published ports bypass ufw.
- `linux/harden-test.sh` checks a box against what `harden.sh` leaves, changing nothing, and is the ad hoc audit for any Linux box; it needs nothing else from the repo: `ssh HOST 'sudo bash -s -- --user NAME' < scripts/bootstrap/linux/harden-test.sh`. It reports SSH (root login, passwords, keyboard-interactive, `AllowUsers` naming the admin user, auth tries, X11), the admin user (sudo, keys), Tailscale (connected), the firewall (ufw active, inbound denied, the tailnet allowed in, public SSH judged against Tailscale: rate limited is a warning, closed while Tailscale is down a failure, and the ports open to the internet), Docker ports published to all interfaces (around ufw), and updates (unattended-upgrades installed and on, the daily timer, pending upgrades, a needed reboot). As root it reads `sshd -T` and `ufw status`; as a user it reads the config files the way sshd does (`sshd_config.d/` first, first value wins) and says which checks need sudo. It exits 0 when every check passes and 1 when any fails; `--brief` prints only the failures, one per line, which is how `install.sh` decides whether to offer `harden.sh`.

## macOS

- `macos/setup.sh` installs the Xcode Command Line Tools when missing and waits for the installer window by polling `xcode-select -p` (`CLT_WAIT_SECONDS` caps the wait), never for a keypress, so closed stdin cannot abort it; then the Xcode license, Rosetta 2 on Apple Silicon, and iTerm2's settings.
- `macos/holeberry.sh` installs Holeberry, the Pi-hole menu bar app, as an optional install on every Mac persona; it has no Homebrew cask, and it counts as installed once `/Applications/Holeberry.app` exists. It reads the latest release's DMG from the GitHub API (without `jq`), mounts it read-only, and copies `Holeberry.app` into `/Applications` only when `codesign` names Holeberry's team (`5UN5GTF749`), the signature verifies, and `spctl` accepts it as notarized; anything else stops with nothing installed. An installed copy is left to Sparkle's updates. `HOLEBERRY_APPS_DIR` changes the destination, which is how the tests run it. The same shape suits another app shipped only as a DMG: a script here with a detect line on its app bundle and that app's team ID.
- Settings outside profiles go in `scripts/bootstrap/macos/iterm2.sh`, which the macOS bootstrap runs: it enables the Python API (needed for Claude Code's split-pane teammates), makes the repo's `dotfiles` profile the default by its `Guid`, and adds each repo `.itermcolors` file to iTerm2's `Custom Color Presets` (so it appears under Color Presets) under its file name, read from the repo so it works before linking. It writes only keys and presets that are missing or differ, and leaves other presets alone. Keep the `Guid` in both files the same. The profile itself is described in [`stow/README.md`](../../stow/README.md).
