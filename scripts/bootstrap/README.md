# scripts/bootstrap/

OS bootstrap that runs before anything is linked (`macos/setup.sh`, `linux/setup.sh`; both take `-n` to report what they would install), `linux/harden.sh` and its check `linux/harden-test.sh`, which `install.sh` offers before anything else on an unhardened server, and the setup scripts `install.sh` applies at the end: the optional installs every persona is offered (a script with a `# detect: COMMAND` line; `# default: off` offers it unticked), and the roles' scripts ([`roles/`](../../roles/README.md): `linux/pihole.sh`). A new setup script is a file here named after its install or role, safe to run again, that skips what is already installed. The installation rules in the [root `AGENTS.md`](../../AGENTS.md) apply here first of all: no reliance on the current PATH, closed stdin never hangs and opts into nothing off by default, and every run is safe to repeat. Which manager installs a package, including system daemons that come through a vendor script here, is in [`homebrew/README.md`](../../homebrew/README.md).

## Linux

- `linux/setup.sh` installs `apt-packages.txt`.
- `linux/pihole.sh` sets up Pi-hole v6 with Unbound as its upstream, the way the [Pi-hole guide](https://docs.pi-hole.net/guides/dns/unbound/) describes and `ph-test` checks. Unbound comes from apt with the guide's `/etc/unbound/unbound.conf.d/pi-hole.conf` (loopback only on `127.0.0.1#5335`, DNSSEC validation, `harden-*`, `hide-*`, the private ranges kept out of answers), Debian's `unbound-resolvconf` hook is disabled (it would make Unbound the box's own resolver with the DHCP servers as forwarders), `net.core.rmem_max` is raised in `/etc/sysctl.d/99-unbound.conf` for `so-rcvbuf`, and `unbound-checkconf` must pass before Unbound is enabled and, when anything changed, restarted; a `dig` against the new socket confirms it answers. Pi-hole then comes from its official installer, unattended: the installer only skips its dialogs when `/etc/pihole/pihole.toml` exists, so a minimal one is written first with the upstreams from `PIHOLE_UPSTREAMS` (default `127.0.0.1#5335`) and `dnssec = false` (Unbound validates), and FTL fills in the rest. An installed Pi-hole is left to `pihole -up`, but every run brings its upstreams and DNSSEC setting back in line through `pihole-FTL --config`. Every run then checks that a web password is set (`webserver.api.pwhash`) and warns when it is not, since without one anyone who reaches the web UI or API can change Pi-hole; `sudo pihole setpassword` sets one. It needs root and re-runs itself through sudo. `PIHOLE_ROOT` prefixes every system path, so the tests run it against a scratch tree with the commands mocked.
- `linux/harden.sh` locks down a Debian server or VPS. It is never run unasked: on a server already in use it closes every port but the tailnet's and the LAN ones below and allows only one SSH user, so `install.sh` only offers it, first, before anything is installed, on a Linux `server` or `vps` that `harden-test.sh --brief` finds unhardened (`--harden` and `--no-harden` answer without a terminal; closed stdin skips it; `HARDEN_ARGS` adds its options). Run from the repo as the admin user, it re-runs itself through sudo for that user (keeping `SSH_CONNECTION` and `TS_AUTHKEY`). Run as root on a box that has no admin user yet, it creates one; it needs nothing else from the repo, so it can be piped over SSH: `ssh root@HOST 'bash -s -- --user NAME --allow 80 --allow 443' < scripts/bootstrap/linux/harden.sh` (`--cloudflare` opens the `--allow` ports only to Cloudflare's ranges, `--lan PORT` opens a port to this box's own network only, `--keep-public-ssh` keeps SSH open to the internet with rate limiting, `-n` is a dry run, and `TS_AUTHKEY` joins the tailnet without a login URL). Everything that can stop it is checked before the first change: a key to give the admin user (root's, or `SUDO_USER`'s; a key tied to a `command=` does not count), the LAN when there are LAN ports (the interfaces with a default route and the subnets routed on them, IPv6 prefixes included; the private ranges when none is found; no default route stops the run), and Cloudflare's ranges, which must look like CIDRs. It then upgrades packages, creates the admin user with passwordless sudo and the keys, installs and connects Tailscale, writes `/etc/ssh/sshd_config.d/00-harden.conf` (keys only, no root login, only that user; checked with `sshd -t` and put back if it fails), sets ufw to deny all inbound except `tailscale0`, Tailscale's UDP port, the `--allow` ports, and the LAN ports on the LAN only, and turns on unattended upgrades. On a Pi-hole (`/usr/bin/pihole-FTL` present) the LAN ports are 53 (TCP and UDP), 80, and 443, plus 67/udp when FTL's DHCP server is on and 123/udp when its NTP server is, so the deny-all default never cuts the network's DNS. Public SSH closes only when Tailscale is connected and this session came in over Tailscale or from the console: `tailscale ip` says the tailnet is up, not that its ACLs let you in, so a session from anywhere else leaves SSH open, rate limited, and says to log in over Tailscale and run again; so does one whose origin cannot be told (a plain `sudo` drops `SSH_CONNECTION`, and `who` is the fallback), and the run says which case it saw. Before enabling ufw it names the services listening on every address that only the tailnet and the LAN rules will reach; without a terminal (an unattended install) it does not wait for a Tailscale login. Running it again rewrites only what differs, but a port an earlier run opened stays open until `ufw delete` closes it. A needed reboot after the upgrade is said at the end. Docker-published ports bypass ufw.
- `linux/harden-test.sh` checks a box against what `harden.sh` leaves, changing nothing, and is the ad hoc audit for any Linux box; it needs nothing else from the repo: `ssh HOST 'sudo bash -s -- --user NAME' < scripts/bootstrap/linux/harden-test.sh`. It reports SSH (root login, passwords, keyboard-interactive, `AllowUsers` naming the admin user, auth tries, X11), the admin user (sudo, keys), Tailscale (connected), the firewall (ufw active, inbound denied, the tailnet allowed in, public SSH judged against Tailscale: rate limited is a warning, closed while Tailscale is down a failure, the ports open to this box's own network listed apart from those open to the internet, and on a Pi-hole a failure when 53 is not allowed from the LAN), Docker ports published to all interfaces (around ufw), and updates (unattended-upgrades installed and on, the daily timer, pending upgrades, a needed reboot). As root it reads `sshd -T` and `ufw status`; as a user it reads the config files the way sshd does (`sshd_config.d/` first, first value wins) and says which checks need sudo, the sudo one included when `/etc/sudoers` or a `sudoers.d` file is unreadable. It exits 0 when every check passes and 1 when any fails; `--brief` prints only the failures, one per line, which is how `install.sh` decides whether to offer `harden.sh`.

## macOS

- `macos/setup.sh` installs the Xcode Command Line Tools when missing and waits for the installer window by polling `xcode-select -p` (`CLT_WAIT_SECONDS` caps the wait), never for a keypress, so closed stdin cannot abort it; then the Xcode license, Rosetta 2 on Apple Silicon, and iTerm2's settings.
- `macos/holeberry.sh` installs Holeberry, a Pi-hole menu bar app with no cask, from its latest release DMG once `codesign` names its team and `spctl` accepts it. Off by default. `HOLEBERRY_APPS_DIR` changes the destination; the tests use it.
- Settings outside profiles go in `scripts/bootstrap/macos/iterm2.sh`, which the macOS bootstrap runs: it enables the Python API (needed for Claude Code's split-pane teammates), makes the repo's `dotfiles` profile the default by its `Guid`, and adds each repo `.itermcolors` file to iTerm2's `Custom Color Presets` (so it appears under Color Presets) under its file name, read from the repo so it works before linking. It writes only keys and presets that are missing or differ, and leaves other presets alone. Keep the `Guid` in both files the same. The profile itself is described in [`stow/README.md`](../../stow/README.md).
